# 产品演示与最终设计基线

## 用户操作

1. 与经理讨论需求。默认选择“先展示产品演示，确认后正式制作”；没有视觉设计需要时可选择跳过。任何项目也都可以主动要求演示。
2. 计划出现后点击“先制作产品演示”（输入“按计划执行”也遵从当前选择）。此时仅授权演示阶段，不启动原计划的完整产品任务。审批卡也提供“跳过演示，直接制作”。
3. 经理可通过现有 MCP 派工、质询和验收；演示产物写在项目的 `.hub-design/<design-id>/draft-N`，不是产品代码。普通按钮只是外观，不实现业务。
4. “查看演示与批注”打开独立阅读窗口：左侧全部页面及父子层级，中间静态画面，右侧箭头说明、框选与反馈；最后为架构/模块/后端/数据流规划。
5. 应用展示全部页面、弹窗及关键状态；视频展示逐镜头故事板；长文档展示全部章节版式。长页面拆成多个单屏画面，避免框选坐标歧义。
6. 可框选区域（坐标相对于1280×900设计画面）、提出 UI 或逻辑意见、重设计当前页或重设计整体。修改启动独立的下一版演示，旧版本不覆盖。
7. 满意后点击“确认最终设计并开始正式制作”。平台将版本与内容摘要绑定正式工作流；原任务与所有后续 Agent 的系统指令均指向此设计基线。经理不能用演示完成冒充真实产品完成。
8. 正式制作安排独立检查者逐页对照布局、字体、颜色、间距、层级、镜头/文档版式，并提供截图或渲染证据；明显偏差需修复，不能擅自改设计。

## Agent 交付契约

演示目录的 `brief.md` 是完整需求、讨论计划、页面基线与本轮修改意见。系统提示词只包含阶段约束与该文件位置，不重复塞全部历史。

交付 `manifest.json`：
```json
{"title":"产品名","pages":[
 {"id":"home","title":"首页","parent":null,"kind":"screen","path":"home.html","note":"→ 顶部导航及操作意图"},
 {"id":"settings","title":"设置","parent":"home","kind":"screen","path":"settings.html","note":"→ 配置分组"},
 {"id":"architecture","title":"架构规划","parent":null,"kind":"architecture","path":"architecture.html","note":"模块、后端、数据与接口规划"}
]}
```
HTML 必须自包含：内嵌 CSS、SVG、data 图片，不用外网字体、脚本、真实接口或业务实现。页面 ID 只用字母数字下划线横线；parent 引用页面 ID。kind 支持 screen/storyboard/document/architecture。每页保持单屏，有箭头和注解；视频/文档用静态故事板/版式样张，不声称已经制作真实视频或完成整篇文档。

经理通过已有 `project_assign` 调度、`project_status` 查状态、`project_complete` 提交。平台检查 manifest 的讨论页面覆盖、层级、文件边界及架构页，冻结为只读用途的版本快照并等待用户审批。文件路径不是操作系统访问沙箱：用户此前授予的完全访问权限不改变，阶段限制由系统指令与工作流控制。

## API 与持久化

`POST /api/action` 支持 design_start、design_skip、design_content、design_feedback、design_accept；完整签名见 frontend-actions.json。均仅用户可调用、按 X-Hub-Project 绑定项目；经理使用既有 MCP，不能替用户批准。

`GET /api/state` 附带当前项目 designs 元数据，不每次轮询重复传 HTML。design_content 返回一小时有效的随机预览能力 URL（不是用户 Token），页面由 sandbox iframe 与独立 CSP 禁止脚本、联网、表单和顶层导航。预览不是产品交互测试。

SQLite design_reviews 记录状态、版本、反馈和确认摘要；HTML 快照在 Hub data/designs 下。重启不丢反馈或版本；原生持续会话按原项目复用。正式验收会检查设计快照摘要，防止悄悄改基线冒充一致。

平台能检查页面清单及提供逐页复核流程，但不能从自然语言自动证明页面已百分之百穷尽，也不能仅靠指令保证像素一致。用户应在确认前核对清单与画面；最终视觉一致性仍需查看实际渲染对照证据。
