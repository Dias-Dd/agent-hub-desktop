# 项目消息归属、经理唤醒与汇报修复（2026-10-21）

## 已确认根因

当前项目a7b989…的经理恢复任务消息在执行记录建立前没有project_id；旧的按时间/发送者猜测归属代码将其分配到已结束旧项目，收据归档器随后归档，真实提交时报“未找到待执行任务消息”。恢复逻辑又把尚无执行的步骤当作已结束，反复创建恢复步骤，现场积累36条。

成员deepseek-3是合法项目成员，但发送时工作流为needs_attention，旧路由仅接受active，笼统显示“没有有效的项目消息授权”。它的完成事件已保存并被认领，但经理执行未能启动。第一轮经理先因写入沙箱拒绝而改派deepseek-2与deepseek-3；派工已通过MCP完成，tasks=[]却被首次计划验证器错误拒绝。

## 修复

- 工作流任务/消息创建时立即赋予项目id；迁移/修正只依据工作流步骤、任务前缀、执行及消息关联，不按发送时间猜测，也不把未知消息塞入默认项目。
- 未启动的经理任务复用；恢复进度只计真正有执行的已结束经理轮次。MCP派工后的tasks=[]合法。
- 成员在active/needs_attention/paused/blocked状态向本项目经理汇报可入队；已结束发送者按持久项目执行上下文定位，保持跨项目隔离。
- 经理轮次不生成成员缺简报提示。普通文字成员结论保留简短片段，标注平台未独立核实，completed仍不等于验收成功；补上汇报时间。
- 平台待交付通知也进入Agent群聊时间线，与已有同内容消息去重。

## 现场恢复

确认没有在途执行，SQLite备份到work/before-live-message-repair.sqlite3，正常关闭自有桌面应用；修正消息归属、恢复成员收件箱，36条从未执行的重复恢复任务合并（保留原任务/消息记录，不重放）。重开新版后经理新检查轮次9db1d2…确已running，deepseek-2/deepseek-3原执行仍completed，项目active。
