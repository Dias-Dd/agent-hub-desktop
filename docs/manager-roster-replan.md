# 成员变化后的经理重新分工

开始制作、首次演示、修改演示及设计确认后的正式实现，在使用历史参与者名单前核对当前身份与已启用接入。停用成员不再进入执行器查找；不恢复停用身份，不按模型名称自动替换，不新增未选择的提供商。

如原执行者或检查者不可用，启动经理重新安排任务与检查职责。完整原批准计划通过 project_status(view="context") 提供，需求、验收和设计基线保持。经理可使用不同模型按能力安排；确有能力缺口时说明。只剩经理时也可进入经理安排阶段，不因没有工作成员而直接拦住。经理本身不可用仍需用户指定可用经理，平台不擅自更换经理。

同类问题：旧检查者身份导致失败、旧首批任务继续派给停用成员、修改演示仍使用上轮参与者，均在同一启动核对逻辑处理。新流程不调用讨论模型重新生成原计划，仅在用户实际点击开始后创建经理调度任务；本次维护未触发生产任务或真实模型推理。

离线验证：roster_replan 5、designs 13、nine_deepseek 6、integrations 21、message_receipts 6、automation 22、harness 26。新增覆盖停用执行者、停用检查者、只剩经理、演示启动及重复批准幂等。测试均模拟提供商。
